## Schema layout (post-unification)

- **Database is Google Firestore with MongoDB compatibility** (host `*.firestore.goog`), not MongoDB. Firestore note: with several concurrent conditional `find_one_and_update` calls on the same doc, only one write lands, but more than one caller can get a document back as if it had won (measured 2026-11-11: 6 concurrent calls, up to 6 "winners", 1 write). Workaround: every `find_one_and_update` goes through `backend.db.find_one_and_update_checked(collection, filter, update, ...)`, which writes a fresh `_writeToken` with the update and only returns the document if it carries that token (None otherwise, as MongoDB would) - never call `collection.find_one_and_update` directly. Also reliable: `update_one(...).modified_count` and `delete_one(...).deleted_count`; `matched_count` is not. Race tests run real parallel requests (`warm_pool` fixture in `tests/conftest.py`): `tests/test_checked_update.py` and the `concurrent` tests in `tests/test_adventures.py`. `tests/test_no_raw_find_one_and_update.py` fails on any direct call.
- **Transactions for multi-document flows** (`backend/db.py` `run_in_transaction`): every public function that writes two or more collections runs in one transaction - `@_in_transaction` in `backend/players.py` (return `BUILD_PLAYER` to answer with the player, built after the commit), `@transactional` from `backend.db` elsewhere (foraging, condition), `run_in_transaction(closure)` in routes (character creation, review rejection). `get_database()` returns a thin wrapper that adds the running transaction's session to every collection call, so helpers join it without passing a session (calls side by side inside one take turns). Returning None (refused) or raising rolls everything back. A write conflict (code 112, TransientTransactionError) re-runs the function after a short random wait, so it must read what it decides on inside itself; after 8 tries `TransactionConflict` -> HTTP 409 "please try again" (`backend/main.py`). Measured on Firestore: atomic across collections, losers get code 112 at once and Motor's own `with_transaction` does not get them through - hence our retry loop. Costs about 30 ms per flow. Keep side effects outside the database (cloud storage, emails) after the commit - a retry repeats everything inside. `tests/test_multi_document_flows_are_transactional.py` checks every public multi-collection function in players/foraging/condition/legend/soul_slots is decorated; race and halfway-failure tests in `tests/test_transactions.py` and `tests/test_transaction_flows.py`. Not used for adventures (`backend/adventures.py`): they have their own statuses, rollback and `recover_adventures`.
- **`player_characters` collection**: `{ address, characters: [{ characterId, name, status: [...], tags: [...], timers: {}, slotNumber, availability: {...}, portraitUrl, activeCraft, ... }] }` — **per-player** (keyed by address). Lightweight summary of all characters: `status` (e.g. `["free"]`, `["adventuring"]`, `["free", "crafting"]`), `tags` (e.g. `["alive"]`, `["dead"]`), `timers` (e.g. `craftingReadyAt`). Profession levels are not mirrored here — read them from the character doc (`profession.lvl1`–`lvl3`). Updated alongside the character doc; injected as `pcStatus`/`pcTags`/`pcTimers` on each character by `_build_player`.
- **`characters` collection**: one doc per character, keyed by `(address, id)`. Each doc holds gear, stats, profession, crafting, availability, etc. `_build_player` assembles a Player from `characters` + related tables.
- **`active_players` collection**: TTL 8h, tracks who is online (address, last_active_at). Separate from character data.
- **`player_vaults` collection**: `{ address, items: [...], itemBalances: {id: qty} }` — **per-player** (keyed by address only). Shared vault across all characters. `itemBalances` is the unified pool for all stackable items (raw materials, processed, crafting tools, food, potions, etc.). `items` holds instance-tracked items. Injected into every `character.vault` by `_build_player` at read time.
- **`character_blueprints` collection**: `{ address, characterId, blueprints: [id, …] }` — soulbound blueprints per character.
- **`character_homes` collection**: `{ address, characterId, items: [...], itemBalances: {id: qty}, homeType: str }` — home storage for out-of-adventure characters. `items` holds instance-tracked gear; `itemBalances` holds stackable counts; `homeType` is a visual hint for the UI background (e.g. `"cave"`, `"forest"`, `"prairie"`, `"ruin"`). Both injected into the character by `_build_player` at read time (`items` → `gear.items`, `itemBalances` → `gear.itemBalances.home`). Only loaded when `inAdventure` is false.
- **`character_resting` collection**: `{ address, characterId, items: [...], itemBalances: {id: qty}, homeType: str }` — rest-stop storage for in-adventure characters at `rest_allowed` story locations. Same schema as `character_homes`. Loaded by `_build_player` only when `inAdventure` is true and `restAllowed` is true. No vault transfers allowed (rest↔vault is always blocked).
- **Unified storage helpers**: Home and rest share generic functions parameterised by `storage_type` (`"home"` or `"rest"`), mapping to their respective collections via `STORAGE_COLLECTIONS`. Generic move functions (`move_storage_item_to_container`, `move_container_item_to_storage`, `load_balance_from_storage`, `unload_balance_to_storage`, `move_container_balance`, `move_container_item`, `bulk_move_storage`, `destroy_all_storage`) enforce transfer rules via `_TRANSFER_RULES` + `_check_transfer`.
- **Transfer rules**: All storage↔container and container↔container transfers are symmetric except vault→body (allowed when `!inAdventure`) vs body→vault (never). Home↔anything requires `!inAdventure`; rest↔anything requires `inAdventure && restAllowed`. Vault↔container (backpack/saddlepack/cart) is never.
- **`Character.gear.items`** on the persistent doc holds only items the character takes on adventure (body, backpack, saddlepack, cart, mount, companion, crafting locations). Home instances live in `character_homes.items`; rest instances live in `character_resting.items`.
- **`Character.gear.itemBalances`** covers `backpack`, `saddlepack`, `cart` on the persistent doc, with `home` injected at read time from `character_homes` and `rest` from `character_resting` (depending on adventure state).
- **`adventure_sessions` collection**: one doc per **running** adventure (`backend/adventures.py`): `{ _id: sessionId, address, storyAuthor, storyId, storyVersion, title, members: [{address, characterId, lead}], status, seq, passage, prevPassage, trail, vars (JSON text), serverVars: {char, lead} }`. Status `starting → active → ending → done`, then the doc is deleted — finished runs never stay here. Every step is a conditional update on `seq`; no multi-doc transactions. `recover_adventures(address)` finishes/undoes anything a crashed request left half done (called on list/start).
- **Character ↔ adventure link**: each member carries `availability.adventure = {sessionId, storyId, title}` on both its `characters` doc and its `player_characters` entry (mirrored by `_sync_pc`), so the soul preview can group characters by `sessionId` without loading sessions. Null when free. The dev in-adventure toggle and character deletion refuse characters in a running session.
- **`adventure_log` collection**: write-once record of each finished adventure (`_id` = sessionId): members, `outcome` (`finished` / `run_away` / `aborted`), `endingPassage`, `trail`, timestamps. Finishing also bumps `stats.adventureFinished`/`adventureRunAway` and adds to `characters.completedStories`; camp storage is discarded.
- **`story_snapshots` collection**: immutable copy of a played story version (`_id` = `author:storyId:hash`), with passages and the step graph (`backend/twine_graph.py`). Sessions pin one, so resubmitting a story never breaks a running adventure. Steps only follow literal `[[links]]`/image-links, plus `Retreat` (if `$meta_allowRunAway`: the StoryInit value, or the scene's own `<<set $meta_allowRunAway to …>>`) and `LastResort` from anywhere.
- **`story_plays` collection**: runs left per player per story (`backend/adventures.py`): `{ address, storyAuthor, storyId, remaining, open: [sessionId] }`, unique on (address, storyAuthor, storyId). The story's `$meta_access` (required at submit) decides the start: `free` = no counter, `trial` = 1, `paid` = 0; a purchase adds 3 (`grant_runs`). Starting takes a run (refused at 0, HTTP 402); a `finished`/`run_away` ending keeps it spent; `LastResort` (`aborted`) or a failed start gives it back. Take/return are conditional writes keyed on the session id in `open`, so retries never double-charge or double-refund.
- **Foraging** (`backend/foraging.py`, rules in `data/foraging-rules.json`, names in `data/foraging-missions.json`): each soul slot gets one pool ever, at `soul_slots.forage_pools.<slot> = {professionCount, total, families: {familyId: {initial, remaining, count}}}`. It's created at character creation, or lazily for older slots. It survives character deletion, and the next character in the slot uses only the families its professions cover. A trip lives on `characters.foraging.activeForage` (pc status `foraging`, timer `foragingReadyAt`). The site gives `floor(base * 0.5 ** (count / halfLife))` per trip (at least 1, at most what's left), with each site's own half-life by its size (`site_half_life`: worked out from the site's size so it empties in about size / `siteUnitsPerTrip` 4 trips, at most `siteTrips` 18 (about 15 days) (`site_trips`) - every site thins out steadily from the first trip's 6-10, small sites are done in a few days - cached per size; `halfLife` 5 only without a known size) - only that leaves the site; gear's bonus comes on top (`dig`: home = taken + taken × bonus, the fraction rounded with a chance - one `bonus_draw` per trip; the site card's range rounds down low and up high; a trip burns at most `maxLightHoursPerTrip` 24h of light - a bigger dig still brings everything home (`light_needed`)), a penalty (darkness) shrinks the find and only the smaller find leaves; `result.fromSite` vs `total` (gathering weapon/items from `data/gathering-bonuses-raw-material.json`, bonus by tier, may drop a condition level per trip (see Item condition); light on ore/crystal/clockwork, only with a tinderbox: each unit the site gives needs 1h (`lightHoursPerUnit`; the gear bonus on top needs none, so a trip needs at most 10h), burned as whole units - lantern oil, then torches, then candles, each lowest tier first (`light_supply` / `plan_burn` / `plan_trip`), hours per unit from `data/light-source-burn-hours.json` (T1 torch 2h; a lantern at the lower of lantern and oil); torch, candle and oil recipes list each ingredient as `alternatives`, overflowing raws first (torch: bone or wood + reed, hide or fiber; candle: hide, monster part, meat or 2 harvest + reed or fiber; oil: fish, monster part or meat + bone, harvest or fiber; likewise leather: 6 hide or 6 skin at the tanning rack, rope: 1 leather or 6 fiber, glass pane: 6 sand or 6 crystal at the kiln, sand first; arrow: bone, reed or wood + feather (classic) or hide; bolt: bone or wood + stone, monster part, crystal or ore; coal: 3 wood or 3 monster part, wood first; six stations are built mostly of stone instead of refined ore - grinding stone, lapidary bench, furnace, mortar & pestle, kiln, alchemy stand - which puts them in CraftStone's starting blueprints too) - crafting takes the first option the crafter has enough of, one option per slot and batch, salvage gives back the first; the blueprint catalog (`craft_catalog._classic_ingredients`) counts only a slot's classic material - the option marked `"classic": true`, else the last consumed one - for profession groups, and a slot forces a tool only if every option needs it, so stand-ins never move an item into other groups (`tests/test_light_recipes.py`, `tests/test_material_alternatives.py`; balance in `docs/balance/raw-material-markets.md`) - and the best light that burned counts like a weapon for the trip (`lightBonusByTier` +25..75%); units the light can't cover are dug as without it (`result.litUnits`/`darkUnits`/`lightHours`; the site card shows "Light for Xh" - green when it covers the highest lit dig, yellow when only the lowest, red when not even that (`light_cover`) - and a range that counts the shortfall; only a light that actually burned sets the bonus): `lightSources`/`lightRequires`/`lightFuel` in `foraging-rules.json`; ore and crystal without a light (`darkness.families`; clockwork only gets the light bonus) find 50% less - only that leaves the site; a trip that runs out of light there counts as dark for the accident roll - and rolls one accident (minor 15% 1-2 / serious 5% 3-5 / hardcore 1% 6-10 temporary Body points, can kill; `result.accident`, applied on collect; sentences `darkAccidents` in `foraging-messages.json`); serious and hardcore also leave the character lost 1-7 days (`lostDays`), one Soul point per day: the trip's real end is `activeForage.returnAt` / pc `timers.foragingReturnAt`, never sent to the browser (`hide_pending_result`, `public_pc_entry`) - after the planned `readyAt` it shows `lost` / pc status `lost`, the soul slot can't be opened (`/full` answers 423) and collecting is refused until back; use `foraging.forage_active` (not `readyAt`) to check whether a character is away; every trip finds at least 1 while the site holds anything), are rolled (with ammo use and gear wear) when the trip starts, kept hidden in `activeForage.result`, and on collect go to the character's home storage (`character_homes.itemBalances`); the result is kept as `foraging.lastResult` with a return sentence from `data/foraging-messages.json` (`rich` / `thin` when more than half is gone / `depleted` on the last trip). Each trip also rolls extras outside the pool (no wear): surprise raws (`surprises`: 5% for 1–3 of any T1–T3 raw, 1% for 1 of any T4–T6) and lost equipment (`oldGear`: 15% for one broken T1 condition-tracked piece of that material's gathering gear, pushed to `character_homes.items`). A site lasts until it's empty: every trip finds at least 1 (`trip_amount`), so late trips give a unit at a time; `forget_site` (POST `.../foraging/forget`, "Forget site" button with a confirm popup) drops what's left for the slot for good (`remaining: 0`, `forgotten: n`), refused while a trip to it is out. An empty site is no longer listed. Foraging, crafting and adventures exclude each other.
- **Your Legend** (`backend/legend.py`): reputation values on the character doc as `legend: {name: 0-100}`, a separate object next to `stats`, names without the `meta_` prefix that stories use (`$meta_mercy` in a story = `legend.mercy`). 20 names in 10 pairs (`LEGEND_PAIRS`); every pair except fame/infamy is one scale, so only one side is above 0. Values are floats (shares of small changes are kept), levels use the whole part. New characters start at 0; reads fill missing names (`legend.with_defaults` in `_build_player`), `scripts/migrate_add_legend.py` writes them into stored docs (dry run by default, `--apply`). Every change goes through `apply_change` (pair scale, fame/infamy pull, one-step echoes, 0-100; numbers in `data/legend-rules.json`) and is written at once by `change_legend` (optimistic `legendSeq` retry; checks `update_one` modified count, not `find_one_and_update` - see Firestore note). No per-adventure tracking: story review guards against loops and oversized changes. Renown fades (`data/legend-rules.json` "decay", 1 point per 7 days, smoothly, never below 0): `legendUpdatedAt` is the last write, `decayed` works the fade out on read, and `change_legend` folds it in and restarts the clock. Nothing calls `change_legend` yet (the story interpreter and the foraging hook are to come). Levels: 0-9 none, 10-29 whispered, 30-59 known, 60-89 renowned, 90-100 legendary.
- **Temporary attribute loss** (`backend/condition.py`): `characters.attr` is the maximum; damage is stored as `attrLost: {attr: n}` (current = max − lost, never below 0) plus `healFrom` (ISO, healing clock). One point heals per 20h of *uninterrupted* free time (`HEALING_INTERVAL_MINUTES` overrides it for local testing), weighted by points lost; the clock restarts after each loss and each return, and is stopped (`healFrom: null`) while foraging/crafting/adventuring (`pause_healing` / `resume_healing`, wired into foraging, `start_craft`/`finish_craft`, adventure claim/release and the dev toggle). Heals are seeded by the clock time, so reads compute the current state (`condition.annotate` → `attrNow`, `attrLost`, `nextHealAt`) without writing. A point aimed at an attribute at 0 goes to another in its group, then to the other group; `vitalStatus` is a list: the life state first (`alive`/`dead`), then conditions - Body all 0 → `["dead"]`, Soul all 0 adds `"soulless"`, and the two stack (`["dead", "soulless"]`; soul intact isn't written); mirrored as the leading pc tags (`backend/character.py` `vital_status_list` reads old one-word docs, `is_alive` / `has_soul`). Only the life state counts for physical actions (foraging, crafting, adventures refuse the dead); soulless is meant to block soul actions such as magic. A drained group never heals. A foraging trip's night (`foraging-rules.json` "nights", sentences in `foraging-messages.json` "nights") is rolled at start: weather from `nights.weather` (`{weight, severity: none|mild|severe, families?}` - weathers with `families` only happen when foraging those materials, e.g. sandstorm on sand, flood on fish/reed/clay, blizzard/rockslide on stone; ore and crystal are dug underground (`nights.underground`) and roll only the weathers marked `underground` - still, damp, draught, dust, creaking, hot_rock, ice_cave, rising_water, foul_air, tremor, ghosts - never the surface ones; a weather with `group` (ghosts: `soul`) sends every point there; a destroyed tent uses the weather's own `tentDestroyed` sentences when it has them; loss by shelter count and severity in `pointsLost`; a severe night has a 3% chance (`tentDestroyedChance`) to destroy the carried tent - the best one is removed at trip start and listed as broken; sentences in `byWeather.<weather>`); tent + bedroll carried = no loss, one of them = at most 1 point, neither = up to 1 Body + 1 Soul; applied on collect.
- **Item condition** (`backend/item_condition.py`, chances in `data/item-conditions.json`): an item instance's `quality` is a condition level 4 new → 3 used → 2 damaged → 1 broken, the same for every tier; below 1 the item is gone. Broken works like new (it's the warning). Wear is a chance to drop one level, not points: foraging rolls once per trip per piece, whatever its tier, when the trip found anything (weapon 10%, item/charm 5%; a bow only when its ammo left a find uncovered) - better gear finds more but wears as fast, so cheap tools are the thrifty choice, crafting rolls once per craft for a borrowed tool item or station (2% per item crafted, added up over the batch, max 50%). Stacked items have no condition but may lose a unit per use (gathering stacks and the tinderbox 2% per trip, tent/bedroll 2% per night). Every `needsItemDefinition` family is condition-tracked (there is no `qualityMax` any more) - including the crafting stations (kind `tool`: anvil, furnace, loom...), and like every tool they only craft recipes at their own tier or below. New items start at 4; lost equipment is found at 1. Mounts/companions show it as Health: Good / Tired / Exhausted / Dying. Salvage penalty by condition: 0 / −10 / −25 / −50%. A damaged item whose recipe holds more than 15 raw units, or a broken one with more than 50, still gives back at least 1 of its most common raw per item (`salvageMinimum` in `item-conditions.json`, applied in `recycling.resolve_salvage_preview`, shown in the salvage window as "+1 saved from the damaged/broken item"). UI: green / yellow / red corner, broken also red tile; popups show "Condition: …". `scripts/migrate_item_conditions.py` turns stations still held as stacked counts into items (dry run by default, `--apply` to write; safe to repeat).
- **Crafting storage** (`backend/players.py` `_craft_storage_type`, `_split_craft_take`, `_craft_return_storage`): crafting never uses the vault. It works from the active storage - home when free, camp (`character_camp`) while resting on an adventure, nothing while on the road - plus what the character carries: stacked balances from storage first, then backpack/saddlepack/cart; item instances from storage, body or the carried bags (`CRAFT_HELD_LOCATIONS`). `activeCraft.storage` records it; the output, flat tools and borrowed storage items return there (a camp craft that outlives its adventure returns home; a craft without `storage`, started before this rule, still returns to the vault). The crafting page is opened from the workbench icon left of the tent at home and at a rest camp.
- **Crafting tiers** (`backend/players.py` `_ingredient_tier_ids` / `_take_across_tiers`, mirrored in `public/craft/recipe-viewer.template.html` `tierIdsFrom` / `takeAcrossTiers`): crafting at tier T accepts any consumed ingredient (raw, processed, final) of tier T or higher - exact tier first, then the next ones up (from the active storage first, then the carried bags - see Crafting storage). The output is always tier T. The viewer shows owned as `exact +higher / needed` (higher in purple). The crafting page (home/camp workbench icon → `CraftingView.tsx`) loads the viewer with `?filters=1` for its All / Craftable / My blueprints radios; character creation omits it. Rebuild the viewer with `python3 public/craft/build-recipe-viewer.py` after editing the template. Starting blueprints: 2 picks from one list (`resource-selection-rules.json` source `any`, `craft_catalog.resolve_blueprint_trapping_options`) - the categories' tools and items, higher tools included, plus the base tools behind them; any combination, no duplicates (checked at character creation). Every armor piece has its own blueprint (`blueprint_<set>_head_armor` / `_chest_armor` / `_leg_armor`, 6 tiers each); `scripts/migrate_split_armor_blueprints.py` turned owned set blueprints into the chest piece's (dry run by default, `--apply`). The crafting tables in `docs/PLAYERS.md` (categories, blueprint XP, no-blueprint XP) are generated between `<!-- BEGIN/END generated: ... -->` markers: rerun `python scripts/generate_crafting_tables.py` after changing recipes or blueprints (`--check` exits 1 when they're out of date).
- **Character deletion** dumps all gear (body, backpack, saddlepack, cart, home, companions, mounts) into the shared vault, deletes blueprints and home doc, discards the rest doc without salvage (temporary adventure loot), then deletes the character doc. The vault persists.



## Submodule: twinejs-integrated

- The integrated Twine story editor lives in the `twinejs-integrated` git submodule (`retro-ai-forge/twinejs-integrated`). Its working branch is **`develop`** — commit and push changes there, not `main`/`master`.
- After committing inside the submodule, record the new commit in the parent repo (`git add twinejs-integrated && git commit`) so the pointer is bumped. A detached-HEAD checkout means the parent is pinning an older commit; `git -C twinejs-integrated checkout develop` to get back on the branch.
- It is served under `/twine/` in the Wudlands app (dev: Next proxies to the vite dev server; prod: built to `public/twine/`). `npm run dev` starts both; `npm run build` builds and copies the editor.
